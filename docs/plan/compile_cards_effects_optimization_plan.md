# compile_cards_effects 后续编译优化实施方案

更新时间：2026-04-15

## 1. 目标与范围

### 1.1 目标

- 在不偏离 `docs/rules/rule.md` 的前提下，持续提升 `tools/compile_cards_effects.py` 的可维护性、可观测性与编译效率。
- 保持“按原子能力建模、禁止按卡硬编码、要求/步骤边界清晰”的既定路线。
- 基于当前正式系列 `cards_raw.json` 的高频文本分布，优先推进“模板家族参数化复用”，降低重复匹配规则和维护成本。

### 1.2 本轮覆盖范围

- 编译器识别层（模板注册、匹配策略、fallback 治理）
- 编译流程层（全量/增量、双遍构建优化）
- 验证与度量层（命中率、冲突检测、回归门禁）
- 文档与执行规范层（计划、日志、验收标准）

### 1.3 非目标

- 不改动 `rule.md` 规则语义。
- 不在运行时引入按卡分支解释逻辑。
- 不把 UI 层逻辑反向塞入规则核心。

---

## 2. 当前基线与问题画像

## 2.1 编译器结构基线

- 入口脚本当前采用模板规则驱动，且触发/事件模板数量较大，已形成可扩展体系，但单文件规模偏大、维护成本持续上升。
- `TemplateRule` 已具备 `priority` 与 `template_metadata` 能力，可作为后续家族化和冲突治理基础。
- 编译流程当前仍保留“先构建语义映射，再重编译产物”的双遍过程。

## 2.2 数据基线（正式 raw）

- 系列目录：`KGD / MCR / MMM / TLR`
- 卡牌总量：442（不含 base sample）
- 触发/效果文本中存在明显高频重复句式（例如抽牌、RAID 触发、AP 激活等），适合收敛为参数化模板族。
- 现状 `Unsupported` 已清零，但后续新增系列仍存在回升风险，需以门禁与统计兜底。

## 2.3 核心问题

1. 模板规模增长快：注册项与 builder 在单文件密集堆叠，新增能力的冲突风险与评审成本上升。
2. 规则复用不足：部分逻辑仍以多段循环/多段正则重复匹配，修改面较大。
3. 可观测性不足：命中统计开关存在，但未作为默认交付数据沉淀。
4. 性能可优化：双遍编译在卡池扩张后会放大编译耗时。

## 3. 约束与设计原则

### 3.1 规则一致性约束

- 全程以 `docs/rules/rule.md` 为最高约束，不得以“优化”名义改变结算语义。
- 涉及高风险区（生命触发、攻击/阻挡、AP/能量支付、胜负判定）时，必须先冻结口径再实施。

### 3.2 DSL/IR 约束

- 新增能力必须先抽象为可复用原子要求/步骤。
- 严禁回退到按卡号硬编码。
- “要求”只做可用性/合法性判断；“步骤”只做状态变化执行。

### 3.3 工程约束

- 保持编译输出字段兼容性（`cards_effects.json` / `cards_semantic.json`）。
- 所有阶段至少补一种有效验证（单元、流程、最小对局、冒烟之一）。
- 每一阶段改动同步更新日志与本计划进度。

## 4. 分阶段实施路线

## 阶段 P0：可观测性与基线冻结（优先级最高）

### 目标

- 建立“模板命中/回退/冲突”度量基线，形成可追踪决策依据。

### 实施项

1. 模板遥测常态化：
   - 输出每次编译的 family/variant 命中次数
   - 输出 fallback 次数与占比
2. 高风险告警：
   - 同文本命中多规则时记录冲突候选
   - 命中顺序变化时输出差异摘要
3. 基线快照：
   - 将关键指标落盘至 `docs/plan/compiler_metrics_snapshot.json`

### 验收标准

- 能稳定产出 metrics 快照并可对比前一轮。
- 新增模板可通过指标定位“是否误伤旧规则”。

---

## 阶段 P1：模板家族参数化收敛（短期主线）

### 目标

- 以 `cards_raw` 高频句式为驱动，减少 exact-by-card 规则与重复 builder。

### 实施项

1. 高频族优先迁移：
   - 抽牌类（含条件抽牌/后续追加）
   - RAID 触发二选一类
   - AP 激活类
2. 统一匹配管线：
   - 将同类“多次遍历 + 多段正则”改为声明式 pattern 列表 + 单次扫描
3. metadata 稳定化：
   - 对同族能力统一 `family` 与 `variant` 命名约定

### 验收标准

- 同族新增文本无需新增按卡分支。
- 同族迁移后语义产物保持一致（步骤序列/要求集合不漂移）。

---

## 阶段 P2：模板模块化拆分（中期）

### 目标

- 降低单文件复杂度与并行冲突概率，提升评审效率。

### 实施项

1. 按 family 拆分模板模块（建议）：
   - `preview_*`
   - `bp_*`
   - `raid_*`
   - `cost_modifier_*`
2. 保留统一注册入口与优先级策略，不改变外部调用方式。
3. 引入最小注册一致性检查（重复 name、缺失 metadata、priority 异常）。

### 验收标准

- 主入口仅保留编译装配逻辑。
- 模板新增流程固定为：定义 → 注册 → 回归，不再跨文件散落。

---

## 阶段 P3：编译流程性能优化（中期）

### 目标

- 减少全量编译耗时，支持系列持续扩容。

### 实施项

1. 双遍优化：
   - 优先实现中间结果缓存，避免重复构建不可变部分
   - 评估单遍编译 + 延迟语义补全可行性
2. 增量编译：
   - 以 `cards_raw.json` 内容 hash 作为输入签名
   - 未变化系列跳过重编
3. 输出一致性守卫：
   - 增量模式与全量模式结果 diff 校验

### 验收标准

- 增量场景下编译耗时明显下降。
- 全量与增量产物语义一致。

---

## 阶段 P4：质量门禁与长期治理（持续）

### 目标

- 防止 `Unsupported` 回升和语义退化，形成长期稳定迭代节奏。

### 实施项

1. 门禁项：
   - `Unsupported` 预算门禁（默认 0）
   - 模板冲突门禁（新增冲突阻断）
2. 回归资产：
   - 高频模板族回归用例自动生成（来自 cards_raw 统计）
   - 长链流程样例持续补齐
3. 文档对齐：
   - 每轮更新 `development_plan` 与当日日志

### 验收标准

- PR 阶段可自动发现并阻断模板退化。
- 新系列导入后可快速识别新增缺口并归入模板族路线。

## 7. 风险与应对

1. 风险：模板泛化过度导致误匹配  
   应对：提高 priority 治理 + 冲突告警 + 最小样例回归。

2. 风险：拆分模块后注册遗漏  
   应对：引入注册完整性检查与 CI 失败快返。

3. 风险：增量编译造成产物漂移  
   应对：强制全量/增量一致性比对，未通过即回退全量。

4. 风险：新系列文本风格突变  
   应对：保留 fallback 与 unresolved 统计，先归类再扩模板族。
