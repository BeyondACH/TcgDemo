# 里程碑计划（基于 `codex/v1.0`）

> 目标：在现有 `cards_effects.json` 与规则引擎原子能力基础上，优先扩大 `SUPPORTED` 覆盖面，再提升运行时稳定性，最后建立可持续的支持率 / 回归体系。

---

## 1. 当前基线

### 1.1 已支持的能力族（`cards_effects.json` 视角）

当前已确认支持的模板 / 能力族包括：

- `CONDITIONAL_DRAW`
- `PREVIEW_TOP_POSITION`
- `OPTIONAL_AP_DAMAGE`
- `HAND_SUMMON`
- `TEMP_BP_MODIFIER`
- `MULTI_BRANCH_CHOICE`

### 1.2 已支持的底层原子能力（规则引擎视角）

#### Requirement

- `TARGET_SET_BP_SUM_LTE`
- `TARGET_SET_DYNAMIC_SUM_LTE`
- `TARGET_SET_UNIQUE`
- `TARGET_SET_DISJOINT`

#### Step

- `SELECT_TARGETS_BY_COMBINATION`
- `SET_CHOICE_MODE`
- `EXECUTE_CHOICE_BRANCH`
- `RUN_COMPOSITE_IF`

#### 组合约束

- `selection_constraints.max_count`
- `selection_constraints.max_sum_bp`
- `selection_constraints.max_sum_provider`

### 1.3 当前开发重点判断

现阶段不建议优先继续堆单卡特判；更适合优先做：

1. 补编译链路，让更多文本族稳定落到已有原子能力上
2. 补运行时回归，保证暂停 / 恢复 / 组合选择 / 分支执行稳定
3. 建立支持率与能力矩阵，形成持续迭代节奏

---

## 2. 总体路线

后续开发按三条主线推进：

### 主线 A：扩大支持面

目标：持续把 `UNSUPPORTED` 迁移为 `SUPPORTED`。

原则：

- 优先按“文本族”补能力，而不是按单卡补特判
- 优先复用已有 requirement / step 原子
- 新能力优先落为稳定命名的 DSL / IR 结构，不走黑盒 fallback

### 主线 B：提升运行时稳定性

目标：保证已支持能力可以正确暂停、恢复、分支、校验和结算。

原则：

- 所有新增模板都要有运行时样例验证
- 所有手动选择 / 分支 / 组合约束能力都要补边界测试
- 修复优先级高于新增低频文本族

### 主线 C：建立质量门与可观测性

目标：让后续开发可量化，不靠体感推进。

原则：

- 每次编译输出都能统计支持率
- 每次核心 handler 变更都能跑固定回归集
- 每次模板扩展都能确认没有大面积退化

---

## 3. 里程碑拆分

## Milestone 1：补齐高价值模板族

### 目标

优先补“已经有底层原子支持，但编译链路尚未充分利用”的文本族。

### 重点事项

#### 3.1 分支子效果模板化

当前 `MULTI_BRANCH_CHOICE` 已支持外层“选择一项”结构，但分支内部效果仍可能以占位形式存在。

本阶段目标：

- 支持“选择一项 → 执行单步效果”
- 支持“选择一项 → 执行复合步骤”
- 支持“分支内再选目标 / 再判断条件”

优先收益：

- 快速减少 `・` 开头文本的 `UNSUPPORTED`
- 提升事件与触发效果的整体支持率

#### 3.2 自动映射 `selection_constraints`

将编译器文本模式自动映射为：

- `max_count`
- `max_sum_bp`
- `max_sum_provider`

并与以下原子对齐：

- `TARGET_SET_BP_SUM_LTE`
- `TARGET_SET_DYNAMIC_SUM_LTE`
- `SELECT_TARGETS_BY_COMBINATION`

优先样例：

- “最多2枚且总BP≤X”
- “从以下目标中选若干枚，总值不超过来源卡提供阈值”
- “多段选择互斥且不可重复”

### 交付物

- 新增模板规则
- 对应 `tests/test_compile_cards_effects.py` 回归用例
- 至少 3 组端到端样例卡
- 文档补充模板映射说明

### 完成标准

- 新增文本族能稳定输出结构化 `requirements / target_specs / steps`
- 目标样例从 `UNSUPPORTED` 迁移为 `SUPPORTED`
- 不引入既有模板退化

---

## Milestone 2：补齐运行时闭环

### 目标

重点解决“编译已支持，但运行时容易出错”的高风险能力。

### 重点事项

#### 3.3 手动选目标的暂停 / 恢复一致性

重点覆盖：

- 候选目标变动后的恢复
- 非法选择恢复时的拦截
- 已选目标上下文的保留与重放
- 多次暂停后的顺序一致性

#### 3.4 组合约束恢复校验

重点覆盖：

- 超数量
- 超总 BP
- 动态阈值边界
- 重复目标
- 与其他集合互斥失败

#### 3.5 分支执行一致性

重点覆盖：

- 未选分支时默认行为
- 分支内暂停 / 恢复
- 分支中再选目标
- 分支执行失败后的上下文行为

#### 3.6 复合条件串联执行

围绕 `RUN_COMPOSITE_IF` 补齐：

- requirement 满足时执行全部 steps
- 中途暂停后的恢复路径
- 某一步失败时的后续语义

### 交付物

- `RequirementMatcher` / `StepExecutor` 单元测试
- 手动选择与恢复的回归测试
- 分支 / 组合约束 / 串联步骤的端到端测试
- 错误码与失败日志口径整理

### 完成标准

- 高风险原子能力均有独立测试覆盖
- 恢复结算不再绕过组合约束
- 分支与复合步骤具备可重复、可验证行为

---

## Milestone 3：建立能力矩阵与支持率体系

### 目标

把开发从“遇到哪张卡修哪张卡”升级为“按文本族和支持率迭代”。

### 重点事项

#### 3.7 支持率统计脚本

输出维度建议包括：

- 每个系列 `SUPPORTED / UNSUPPORTED` 数量
- 每个模板族的覆盖卡数
- 高频 `UNSUPPORTED` 文本聚类
- 新增能力前后的支持率变化

#### 3.8 原子复用矩阵

输出维度建议包括：

- 每个 requirement.type 被多少模板使用
- 每个 step.type 被多少模板使用
- 哪些原子已实现但产出率低
- 哪些文本频繁出现但缺原子表达

#### 3.9 回归快照机制

建议建立：

- 编译产物结构快照
- `SUPPORTED / UNSUPPORTED` 总数快照
- 重点卡牌样例快照

### 交付物

- 支持率统计脚本
- 原子复用矩阵报表
- 编译快照与对比脚本
- 周期性更新文档模板

### 完成标准

- 能定量看到每次迭代的支持率提升
- 能快速定位回归来源
- 能指导下一批模板开发优先级

---

## 4. 测试策略升级

后续测试建议分四层建设：

### 4.1 编译器模板测试

目的：确认文本到 DSL / IR 的映射稳定。

检查项：

- `status`
- `template_metadata`
- `requirements`
- `target_specs`
- `steps`

### 4.2 原子 handler 测试

目的：确认 requirement / step 原子自身行为正确。

检查项：

- 输入上下文解析
- 边界值处理
- 非法值兜底
- 返回结构一致性

### 4.3 端到端效果测试

目的：确认从能力编译到执行结算的完整闭环。

检查项：

- 是否暂停
- 是否发起正确选择
- 是否正确恢复
- 是否正确修改状态
- 是否正确产生日志 / 错误

### 4.4 回归快照测试

目的：防止模板扩展造成整体能力退化。

检查项：

- 编译产物结构差异
- 支持率差异
- 重点样例卡差异

---

## 5. 开发规范建议

### 5.1 新能力准入规则

每新增一个能力族，至少同步交付：

- 规则文档中的原子定义或模板归类
- 至少 1 个编译样例
- 至少 1 个运行时样例
- 至少 1 个失败边界样例
- 与已有原子的复用说明

### 5.2 代码设计规则

- `requirement.type` 与 `step.type` 使用稳定命名
- 避免黑盒 fallback 承载业务语义
- 优先抽象成可复用模板，不为单卡硬编码解释路径
- 编译器新增能力时同步考虑运行时测试与日志口径

### 5.3 文档同步规则

每次新增能力时，同步更新：

- `docs/rules/rule.md`
- `docs/logs/*.md`
- 相关测试说明
- 样例卡列表

---

## 6. 推荐执行顺序

### 迭代 1

- 补 `・` 分支子效果模板化
- 补 `selection_constraints` 编译映射
- 增加“组合约束 + 分支”端到端样例

### 迭代 2

- 补手动选目标暂停 / 恢复回归
- 补组合约束恢复校验
- 补 choice 分支与复合条件串联测试

### 迭代 3

- 建支持率统计脚本
- 建原子复用矩阵
- 建编译产物快照与回归机制

### 迭代 4

- 依据支持率结果继续清理高频 `UNSUPPORTED`
- 收敛模板边界与 DSL 口径
- 固化新增能力准入 checklist

---

## 7. 一句话结论

后续最优先路线不是继续零散加单卡特判，而是：

1. 先补编译器映射，把已有 runtime 原子吃满
2. 再补暂停恢复 / 组合选择 / 分支执行的稳定性
3. 最后用支持率与能力矩阵驱动后续迭代
