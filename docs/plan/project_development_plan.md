# TcgDemo 项目开发计划

## 1. 计划摘要

当前仓库已经完成一个可运行的 MVP：开局初始化、阶段推进、基础出牌、能量校验、攻击/阻挡、伤害结算、胜负判断、基础 UI 与冒烟脚本均已具备。后续开发按 `docs/rules/rule.md` 优先补齐高风险规则区，再扩展效果系统与数据能力，最后完善 UI/调试体验。

涉及 `core + data + ui` 的改动，必须先由主 agent 锁定接口，再按 `core`、`docs/tests`、`ui` 三线并行推进。

建议分 4 个里程碑推进：

1. 规则闭环补完
2. 效果系统与关键词扩展
3. 数据契约、导入与自动化验证
4. UI/交互与调试体验完善

## 2. 里程碑 1：规则闭环补完

目标：把当前 MVP 补到与 `docs/rules/rule.md` 一致的稳定最小规则集。

### TurnManager

- 补齐开始阶段与结束阶段的完整顺序语义：起始重置、AP 增长、首攻首回合不抽、额外付 1AP 抽 1、结束阶段手牌上限处理、仅角色/场地恢复 ACTIVE、AP 不恢复。
- 将开局流程补齐为“起手 7 张 -> 双方依次一次换牌决策 -> 再放置 7 张生命牌 -> 进入首回合”，避免继续用当前的直接发手牌/生命的简化逻辑。
- 将当前“超手牌直接移除”改为显式弃牌决策流程；若当轮不做 UI 选择，则先冻结为待决策接口，不继续写死自动丢弃。

### RulesEngine

- 补齐区域容量与落点规则细节：前线 4、能量线 4、AP 3、场地牌只能进能量线。
- 补齐移动阶段规则：仅能量线角色可常规前移；带 `STEP` 的角色允许前线退回能量线，并支持满位时交换。
- 补齐出牌合法性中的“挤出/替换/无法落位”决策语义，避免继续依赖当前简化逻辑。

### BattleResolver

- 按 `docs/rules/rule.md` 固化攻击、阻挡、结算顺序。
- 补齐“攻击玩家”与“攻击角色”的分支语义。
- 保持“攻击失败的攻击方不会退场”这一 UA 特殊规则。
- 预留狙击类指定攻击接口，但当前阶段只把主流程和阻挡时点做稳。

### EffectResolver

- 将生命区受伤后的触发从“自动触发”改为“可选择是否发动”的决策模型。
- 引入触发队列，而不是发现即执行，为后续“同时触发顺序”做准备。

### ZoneManager / VictoryChecker

- 明确退场、移除、生命翻出、抽空牌库失败的统一处理入口。
- 保证胜负检查在伤害结算、抽牌失败、生命归零三个关键节点都能稳定触发。

### 推荐拆分

- Agent A：`core/turn + rules + battle` 主逻辑
- Agent B：`docs/` 与规则/回归测试脚本
- Agent C：仅做 UI 适配，只消费已冻结的新接口

## 3. 里程碑 2：效果系统与关键词扩展

目标：从“少量硬编码效果”升级到可持续扩展的效果框架。

- 当前优先子阶段：`docs/plan/todo.md` 中 P0、核心 P1 与剩余 P1 已全部补齐；当前进入效果系统收尾与回归阶段，重点维护“临时产能修饰 + 延迟自退场”“绑定自身的临时特殊登场/RAID 许可”等高阶模板的稳定性。

### 效果契约冻结

- 统一 `CardDef.effects` / `trigger_effects` 字段命名，明确 `trigger / condition / cost / target / operations / once_per_turn` 结构。
- `GameState` 增加 `effect_queue`、`battle_context`、待决策容器。
- `CardInstance.flags` 明确每回合攻击、阻挡、主动技次数等状态位。

### EffectResolver 扩展

- 支持 `MAIN_ACTIVATE`、`ON_LEAVE`、`ON_BATTLE_WIN`、`ON_BATTLE_LOSE`、`ON_BATTLE_END`。
- 增加基础 `condition` / `cost` / `target` 解析，至少覆盖：自身、攻击者、阻挡者、目标玩家、我方前线、敌方前线、生命牌。
- 支持 `once_per_turn` 校验与重置。

### 关键词与战斗扩展

- 第二批实现 `STEP`、`RAID/突进`、`DAMAGE_2`、`IMPACT/冲击`、`IMPACT_PLUS_1`、`NEGATE_IMPACT/冲击无效`、`DOUBLE_ATTACK`、`DOUBLE_BLOCK`。
- `RAID` 相关的 `stacked_under` 与离场处理必须与 `docs/rules/rule.md` 一致，不能简化成普通替换登场。
- 当 `RAID` 目标在能量线时，接口需允许玩家显式选择叠放后留在能量线或转到前线；当目标在前线时只能留在前线。

### 数据联动

- 更新样例卡数据，加入覆盖上述机制的最小卡组样本。
- UI 只做消费：展示关键词、可发动按钮、待选触发，不反向承载规则判断。

### 推荐拆分

- Agent A：`EffectResolver` 与触发队列
- Agent B：卡牌数据与样例
- Agent C：测试脚本，不改规则主逻辑

## 4. 里程碑 3：数据契约、导入与自动化验证

目标：把“能跑”提升到“可持续迭代”。

### 数据层

- 统一 `data/cards/base_cards.json` 的字段格式、编码和命名，消除文档、终端与数据之间的命名漂移。
- 为卡牌定义增加静态校验：类型、费用、产能、关键词、触发器字段是否合法。

### 导入工具

- 强化 `docs/deck_importer.gd` / `docs/import_deck.gd`，补齐错误报告、缺卡提示、数量校验、主卡组 50 张约束。
- 导入后的 deck JSON 必须与运行时结构一一对应。

### 自动化验证

- 在现有 `docs/milestone_smoke_test.gd` 基础上扩成“规则冒烟 + 数据冒烟”双层脚本。
- 新增针对高风险区的最小对局脚本：攻击/阻挡、生命触发、区域容量、AP/能量支付、回合切换。
- 保持每次规则改动后至少可执行一次 headless 冒烟。

### 推荐拆分

- Agent A：数据校验与导入工具
- Agent B：冒烟/回归脚本
- Agent C：文档整理

## 5. 里程碑 4：UI/交互与调试体验

目标：让规则能力可见、可操作、可验证。

### GameManager 快照

- 在规则接口冻结后扩展 `GameManager.get_snapshot()`：待发动触发、可选目标、战斗上下文、AP/能量可用信息、关键词与叠放信息。

### UI

- 为双方战场增加位于左侧的生命区盖牌展示，并复用待决策面板承接开局换牌交互。
- 增加显式决策交互：生命触发是否发动、结束阶段弃牌、主动技发动、目标选择、`STEP/RAID` 相关动作。
- 优化战斗提示：当前攻击者、可阻挡者、战斗结果、触发排队状态。
- 保持 UI 只消费快照和信号，不写规则。

### 调试能力

- 增加日志分类、调试面板或开发者快照查看，方便核对规则状态。
- 对常见非法操作给出明确原因，而不是笼统失败。

### 推荐拆分

- Agent A：`ui/` 交互
- Agent B：`GameManager` 轻量快照补充
- Agent C：交互回归验证

## 6. 关键接口冻结项

在实施前由主 agent 统一冻结以下接口，再允许并行：

- `GameState`
  - 新增 `effect_queue`
  - 新增 `battle_context`
  - 新增待决策容器，例如 `pending_choice` / `pending_choices`
- `CardInstance.flags`
  - 固定回合内标记字段，供攻击、阻挡、主动技、二次攻击/阻挡复用
- `EffectResolver`
  - 统一入口为“入队触发、处理队列、执行 operation、返回日志/待决策”
- `GameManager`
  - 增加处理玩家决策的入口，如：生命触发选择、弃牌选择、主动技选择、目标选择
  - `get_snapshot()` 扩展但需保持 UI 兼容，不要在未冻结前让多个 agent 同步改快照
- 卡牌 JSON
  - 统一 `effects` / `trigger_effects` 的字段格式，避免脚本与数据各自解释

## 7. 测试计划

必须覆盖以下场景，并按里程碑逐步补齐：

- 开局：50 主卡组、7 手牌、7 生命、首攻/后攻 AP 与抽牌差异
- 开局换牌：双方依次一次换牌决策、不换牌时生命区按当前牌库顶部放置、换牌时先重抽再把原手牌洗回牌库
- 回合：`START -> MOVE -> MAIN -> ATTACK -> END` 顺序，结束后切换行动方
- 区域：前线上限 4、能量线上限 4、场地牌不能进前线、AP 上限 3
- 资源：AP 支付、能量颜色校验、额外 1AP 抽 1 的每回合限制
- 战斗：攻击玩家、阻挡、BP 比较、攻击失败攻击方不退场
- 生命：受伤翻生命、生命触发可选发动、生命归零立即胜负
- 牌库：开始阶段抽牌失败导致败北
- 关键词：`STEP`、突进、二次攻击/阻挡、冲击系效果
- 叠放：`RAID/突进` 叠放登场、离场时上层/下层去向
- UI 回归：可选择阻挡、可选择触发、非法操作提示、快照字段正确消费

## 8. 实施假设

- 当前版本仍以本地 1v1 原型为目标，不规划网络同步。
- 短期内不引入复杂动画或美术重构，UI 优先服务规则可见性和可测试性。
- `docs/rules/rule.md` 高于 README 和现有实现；若现状与规则冲突，以 `docs/rules/rule.md` 为准。
- 所有跨层改动默认先冻结接口，再按 `core`、`docs/tests`、`ui` 三线并行。
- 同一轮并行开发中，不允许两个 agent 修改同一个 `.gd` 文件。
