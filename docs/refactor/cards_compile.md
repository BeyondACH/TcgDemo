# `compile_cards_effects.py` 识别层重构实施蓝图

## 1. 背景与问题

当前 `tools/compile_cards_effects.py` 的主要问题不是单纯文件过长，而是“文本识别、能力组装、少量卡号特例、未支持回退”混在同一层顺序判断里。随着正式卡池和支持模板继续增长，继续沿用 `if text == ...` / `re.fullmatch(...)` 的线性堆叠方式，会持续放大以下问题：

- 新增模板时难以判断插入位置，容易误伤既有优先级。
- 通用模板与按卡特例混杂，复用边界不清晰。
- `_compile_trigger`、`_compile_event_effect`、`_compile_passive_effect` 会继续膨胀。
- 后续若要统计模板命中、排查漏识别、定位误匹配或做局部回归，观察成本偏高。

本蓝图的目标不是引入新的运行时效果能力，而是把识别层重构为“模板注册表 + 参数化 builder + 明确回退链路”的结构，使后续扩展入口稳定、可观察、可验收。

## 2. 非目标与边界

本轮重构只覆盖 `tools/compile_cards_effects.py` 的识别层组织方式，不包含以下事项：

- 不新增 DSL/IR 原子 requirement、target、step、cost 或新的运行时字段。
- 不修改 `data/cards/*/cards_effects.json`、`data/cards/*/cards_semantic.json` 的对外结构。
- 不修改 `core/effect_resolver.gd`、`DeckImporter`、`GameManager` 的运行时消费契约。
- 不把识别规则外置成 JSON 或其他配置文件。
- 不允许把暂时无法表达的正式卡文通过按卡硬编码强行接入运行时。

如果某类文本无法由现有 IR 稳定表达，应先单独立项扩展 DSL/IR 原子能力，再回到识别层重构；本蓝图不承担该类扩展决策。

## 3. 核心完成标准

本蓝图的完成标准不是“注册表化”，而是“同类文本参数化复用同一模板族”。

### 3.1 算完成

满足以下条件才视为完成：

- 同一类文本命中统一模板族，而不是继续散落为多个逐句模板。
- 同族文本复用同一 builder 与同一原子步骤主链，仅通过参数表达差异。
- `_compile_trigger`、`_compile_event_effect`、`_compile_passive_effect` 退化为调度入口，不再持有大段识别细节。
- 未支持项仍保留显式回退链路，并且可以观察命中与回退结果。

### 3.2 不算完成

以下情况明确不视为完成：

- 只是把现有 `if text == ...` 搬入注册表，但 builder 仍按逐句拆散。
- 同类卡文仅因名称、特征、预览张数或是否追加弃牌不同，就继续新增特例模板。
- 主编译函数表面变短，但识别复杂度只是转移到多个逐句函数中，没有形成可复用模板族。

## 4. 术语与统一约定

为避免实现和验收时混用近义词，本蓝图统一采用以下术语：

- `matcher`
  - 负责判断一段卡文是否命中模板，可为精确匹配、正则匹配或受限谓词匹配。
- `registry`
  - 某一时机下的模板注册表，按优先级保存多个模板规则。
- `builder`
  - 命中模板后负责组装 `requirements`、`target_specs`、`steps` 并返回能力对象的构造函数。
- `template family`
  - 共享同一 builder 和步骤主链、仅通过参数表达差异的一组同类文本模板。
- `card-specific template`
  - 暂时无法收敛为通用模板族、但仍必须纳入统一注册表管理的受限特例模板。
- `fallback`
  - 模板未命中或当前明确不支持时进入的现有回退链路，例如 `semantic_map` 分析与 `UNSUPPORTED` 能力输出。
- `telemetry`
  - 用于观察模板命中、未命中和优先级误吞情况的最小统计与调试辅助。

后文中的“模板”一词默认指“注册表中的模板规则”，不再混指“旧分支”或“任意 if 判断片段”。

## 5. 目标架构

### 5.1 调度入口

以下入口函数重构后只负责调度，不再承载大段识别实现：

- `_compile_trigger`
- `_compile_event_effect`
- `_compile_passive_effect`

统一调度流程如下：

1. 读取 `event_name`、`text`、`card_id` 与必要语义上下文。
2. 根据时机选择对应的模板 `registry`。
3. 按优先级顺序遍历模板。
4. 首个命中的模板调用其 `builder` 生成能力对象。
5. 若全部未命中，则进入现有 `fallback` 链路。

### 5.2 模板规则最小契约

每条模板规则至少应包含以下信息：

- `name`
  - 模板名称，用于调试、统计和验收。
- `event_filter`
  - 适用时机，例如 `ON_ENTER`、`ON_PLAY`、`MAIN_ACTIVATE`、`ON_LIFE_TRIGGER`。
- `matcher`
  - 文本匹配器，支持精确匹配与正则匹配。
- `card_filter`
  - 可选的卡号白名单或谓词，仅用于受限特例。
- `builder`
  - 返回统一 DSL/IR 能力对象的构造器。
- `priority`
  - 控制匹配顺序，具体模板优先于泛化模板。
- `kind_override`
  - 可选，用于覆盖 `TRIGGERED` / `ACTIVATED`。
- `unsupported_reason`
  - 可选，用于显式标注部分支持或当前不支持原因。

模板规则只负责两件事：

- 判断当前文本是否命中。
- 将命中的文本映射为统一 DSL/IR 能力对象。

模板规则不负责写文件，不负责跨模板决策，也不直接修改运行时契约。

## 6. 模板族策略

### 6.1 通用模板优先

重构后优先维护可复用于多张卡的通用模板族，例如：

- 固定抽牌
- 单体退场
- 目标选择后移动
- 生命区回手后二次结算
- AP 激活
- 预览牌库后加手并重排
- 预览牌库后登场并重排
- 临时 BP 修正
- 临时关键词授予

这类模板必须优先复用现有原子 requirement / target / step 组合实现，不允许重新引入按卡解释逻辑。

### 6.2 `UA31BT_MMM_1_007` 作为主示例模板族

`UA31BT_MMM_1_007` 所代表的“预览牌库后按名称/特征加手并重排”必须作为本次重构的主示例模板族，而不是孤立个案。该模板族应统一复用现有 `_preview_add_to_hand_then_reorder_steps(...)`，通过参数注入差异，而不是继续为整句文本复制 builder。

该模板族至少应固定以下参数槽位：

- `preview_count`
- `candidate_filters`
- `candidate_requirements`
- `discard_after_add`
- `reorder_to_position`

默认视为同族变化、应由参数表达而非新增特例的情况包括：

- 预览张数变化
- `NAME_IS` 候选变化
- `HAS_TRAIT` 候选变化
- `NAME_IS` 与 `HAS_TRAIT` 的 OR 组合
- `NAME_IS` 排除后再按特征筛选
- 成功加入手牌后追加弃 1 张
- 剩余卡返回牌库顶部或底部

文档中应明确将以下文本变体归入同一模板族：

- `〈某名称〉或［特徴：某特征］`
- `［特徴：某特征］`
- `〈某名称〉以外の［特徴：某特征］`

只有当文本引入新的步骤组合、额外条件结算，或现有 builder 无法表达的控制流时，才允许脱离该模板族并登记为新的受限特例。

### 6.3 受限特例模板

受限特例模板仅用于以下场景：

- 当前文本模式尚未抽象成稳定通用模板族。
- 某些卡在相同文本语义下存在额外限制条件。
- 需要短期保持既有支持结果，后续再继续泛化。

即使是特例模板，也必须进入统一注册表，不允许重新散落回主调度函数中继续堆叠 `if card_id == ...`。

同时增加硬约束：如果某张卡与既有模板相比，变化仅限于筛选值、名称、特征、预览张数或是否追加弃牌，则不得以“先兼容再说”为由登记为新的特例模板。

## 7. 复用现有构造器的原则

识别层只负责“匹配哪种文本模式”，能力构造层负责“如何用既有 IR 表达这类模式”。因此后续 builder 应优先复用现有构造器，例如：

- 手动单体目标选择
- 上下文目标选择
- 从手牌过滤登场
- 从场外过滤登场
- 预览牌库后加手并重排
- 预览牌库后登场并重排
- 保留顶部其余送场外

builder 不应在主流程里直接拼长段 steps。若某个模板族无法复用既有构造器，应先判断是：

- 仍可通过参数化复用同一主链
- 还是需要单独扩展新的通用构造器

默认不接受“因为赶进度而在 builder 中重新写一段按卡步骤串”的做法。

## 8. 迁移蓝图

### 阶段 1：建立 matcher / registry / builder 契约

目标：

- 抽出统一模板规则结构。
- 封装精确匹配与正则匹配入口。
- 封装注册与按优先级遍历机制。
- 保留 `_supported_ability`、`_unsupported_ability` 作为最终出口。

阶段完成判据：

- 主编译入口已能通过统一调度遍历模板。
- 旧识别逻辑允许暂时并存，但必须开始向注册表迁移。
- 契约已足够支撑通用模板族与受限特例共存。

### 阶段 2：迁移高复用模板族并完成参数化归并

优先迁移最稳定、最重复、最容易产生后续收益的模板族：

- 抽牌类
- 退场类
- 目标选择并移动类
- 临时 BP / 临时关键词类
- 预览牌库类
- 生命区回手后二次结算类

该阶段的重点不是“迁移数量”，而是“建立参数化归并范式”。至少要完成以下收口：

- 识别每个模板族的固定部分与可变参数。
- 优先收口预览牌库类中已经重复出现的文本模式。
- 对现有分支建立归并表，至少覆盖：
  - 纯名称匹配
  - 纯特征匹配
  - 名称/特征 OR 匹配
  - 名称排除 + 特征匹配
  - 加手成功后追加弃牌

阶段完成判据：

- 同族新增文本默认只需补参数抽取，不再新增 builder。
- `UA31BT_MMM_1_007` 一类文本已明确落在同一模板族，而非多个注册表条目。

### 阶段 3：收口残余卡号特例

目标：

- 把散落在 `_compile_trigger`、`_compile_event_effect` 中的卡号特例统一搬入受限特例注册表。
- 让主调度函数不再感知具体卡号。
- 对具备继续泛化空间的特例增加后续合并标记。

阶段完成判据：

- 主入口不再出现按卡号分支堆叠。
- 残余特例的存在理由清晰、数量可观察、后续归并方向可追踪。

### 阶段 4：补 telemetry、自检与回退观察点

建议加入最小可观测性：

- 模板名称
- 模板命中次数
- 未命中回退计数
- 可选调试输出开关

阶段完成判据：

- 可以快速定位哪些模板命中异常下降。
- 可以确认泛化模板是否误吞更具体模板。
- 可以确认未支持项是否仍集中在值得扩展的模式上。

## 9. 外部不变与内部允许重组

### 9.1 外部不变

本次重构不改变以下对外契约：

- `data/cards/*/cards_effects.json` 的结构。
- `data/cards/*/cards_semantic.json` 的结构。
- `abilities[*].timing / requirements / target_specs / steps / limits / ui / status` 字段形状。
- `core/effect_resolver.gd` 的运行时消费方式。
- `DeckImporter`、`GameManager` 对编译产物的读取方式。

### 9.2 内部允许重组

允许变化的仅限于识别层内部组织方式，例如：

- `_compile_trigger`、`_compile_event_effect`、`_compile_passive_effect` 从长链判断改为调度入口。
- 模板函数和 builder 的拆分方式。
- 注册表与 matcher 的组织方式。
- 统计、调试和回退观察信息的内部实现方式。

## 10. 验收标准

### 10.1 编译回归

执行：

```powershell
python tools/compile_cards_effects.py
```

检查：

- 能正常生成 `cards_effects.json`。
- 能正常生成 `cards_semantic.json`。
- 已支持 / 未支持统计不出现非预期回退。

### 10.2 产物等价性检查

至少抽样复核以下模板族的输出主链保持一致：

- 固定抽牌
- 单体退场
- AP 激活
- 预览牌库后加手
- 预览牌库后登场
- 临时 BP / 临时关键词授予

重点检查：

- `timing`
- `requirements`
- `target_specs`
- `steps`
- `status`

### 10.3 同族兼容性验收

围绕 `UA31BT_MMM_1_007` 所代表的模板族，至少确认以下事项：

- 准备一组仅替换特征名的假想文本或样例文本，确认其命中同一模板族，而不是落为新的逐句模板。
- 对“名称或特征”与“名称排除 + 特征”两种变体，确认最终 `steps` 主链保持一致，只允许 `filters` / `requirements` 差异。
- 若启用模板统计，这些文本应命中同一模板名或同一模板族标识。
- 对产物比对，重点确认以下主链不会因参数变化而分叉为新的专用实现：
  - `PREVIEW_TOP_DECK`
  - `SELECT_TARGETS`
  - `MOVE_SELECTED_CARDS`
  - `REORDER_CONTEXT_CARDS`

### 10.4 模板命中自检

若加入 telemetry，应至少确认：

- 每类核心模板都存在命中记录。
- 未出现所有文本都落回 `UNSUPPORTED` 的异常。
- 泛化模板不会吞掉更具体模板的命中机会。

### 10.5 文档层验收

重构后的文档应满足以下要求：

- 章节顺序能直接回答“为什么做、边界在哪、准备怎么做、什么算完成、如何验收”。
- 实现者不需要再自行决定“先迁什么、什么算特例、何时算完成”。
- “注册表化不等于完成”的约束在文档中可直接扫描到，而不是埋在段落细节里。

## 11. 风险与回退策略

- 若泛化模板优先级设置不当，可能提前命中特例文本，导致行为细微偏差。
- 若正则迁移时处理不当，可能把“固定值模板”和“动态阈值模板”错误合并。
- 若只完成注册表化而未做模板族参数化归并，后续仍会重复制造“换一个 trait/name 就新增模板”的维护成本。
- 若某张卡当前仍无法由现有 IR 稳定表达，保持 `UNSUPPORTED` 比引入新的按卡硬编码更安全。

默认回退原则：

- 先保证外部产物和运行时契约不变。
- 若某个泛化模板引发行为不确定，优先缩小匹配范围或暂时降回受限特例模板，而不是牺牲运行时契约。
- 若识别层重构进行到一半，只做到注册表迁移而未完成模板族归并，则必须在文档和实现状态中明确标记“未完成”，不得宣称目标已达成。

## 12. 预期收益

本蓝图完成后的收益应面向实施验收，而不是停留在抽象表述：

- 新增同族文本时，默认只补参数抽取，不新增 builder。
- 主编译入口更短、更稳定，识别职责与构造职责边界更清晰。
- 模板命中、误匹配和未支持分布更容易被观察与回归。
- 后续继续扩正式卡文时，更容易判断应落到“已有模板族、受限特例，还是先扩 DSL/IR”哪条路径。
