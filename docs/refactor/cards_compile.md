# `compile_cards_effects.py` 识别模式重构方案

建议落盘路径：`docs/refactor/compile_cards_effects_recognizer_refactor.md`

## 概要

当前 `tools/compile_cards_effects.py` 的主要问题不是单纯文件过长，而是“识别规则、能力构造、少量卡号特例、回退逻辑”混在同一层顺序判断里。随着效果文本和支持卡池继续增长，继续沿用 `if text == ...` / `re.fullmatch(...)` 的线性堆叠方式，会持续放大以下成本：

- 新增模板时难以判断应插入的位置，容易误伤已有优先级
- 通用模板与按卡特例混杂，复用关系不清晰
- `_compile_trigger`、`_compile_event_effect`、`_compile_passive_effect` 会持续膨胀
- 后续想统计模板命中、排查漏识别、做局部回归都不方便

本次重构的目标是将识别模式改为“模板注册表 + 通用能力构造器”的结构，在不改变现有 `cards_effects.json` / `cards_semantic.json` 输出契约的前提下，降低维护成本并为后续扩展留出稳定入口。

## 重构目标

- 将“文本识别”与“能力组装”从主编译函数中拆开
- 将通用模板与按卡特例统一纳入注册表管理
- 保持现有 DSL/IR 输出字段不变，不修改运行时消费契约
- 让新增效果支持时，优先表现为“新增模板”而不是“继续扩展大函数”
- 保留未支持能力的回退链路与 `semantic_map` 分析能力

## 同类原子能力兼容性原则

“兼容同类原子能力”在本次重构中的含义是：当两张卡的 DSL/IR 步骤顺序、状态变化语义与目标选择流程一致，只是筛选条件、候选名称、特征值、预览张数或少量数值参数不同，就必须复用同一模板族，而不是继续新增独立的逐句模板。

默认视为“同类变化”的范围包括：

- 预览张数变化
- `NAME_IS` 候选变化
- `HAS_TRAIT` 候选变化
- 是否在成功加入手牌后追加弃 1 张
- 剩余卡返回牌库顶部或底部

对这些变化，重构后的识别层必须优先把差异表达为模板参数，而不是继续堆叠新的 `if text == ...` 或“注册表中的逐句特例模板”。如果只是把现有精确文本匹配搬入注册表，而没有收口为同一 builder + 参数输入，则仍不视为完成“兼容同类原子能力”的目标。

## 设计方案

### 1. 引入统一模板规则模型

为识别层引入统一的模板描述结构。每条模板至少包含以下信息：

- `name`
  - 模板名称，用于调试和统计命中情况
- `event_filter`
  - 适用时机，例如 `ON_ENTER`、`ON_PLAY`、`MAIN_ACTIVATE`、`ON_LIFE_TRIGGER`
- `matcher`
  - 文本匹配器，支持精确文本匹配和正则匹配
- `card_filter`
  - 可选的卡号白名单或谓词，用于保留少量必要的按卡特例
- `builder`
  - 命中后负责组装 `requirements`、`target_specs`、`steps` 并返回能力对象
- `priority`
  - 用于控制模板匹配顺序，具体模板优先于泛化模板
- `kind_override`
  - 可选，用于覆盖 `TRIGGERED` / `ACTIVATED`
- `unsupported_reason`
  - 可选，用于部分支持或显式未支持模板

模板规则只负责两件事：

- 判断当前卡面文本是否命中
- 将命中的文本映射为统一 DSL/IR 能力对象

模板规则不负责直接写文件，不负责跨模板决策。

### 2. 将主编译入口改为调度器

把以下函数改造成调度器，而不是长链判断：

- `_compile_trigger`
- `_compile_event_effect`
- `_compile_passive_effect`

调度流程统一为：

1. 读取 `event_name`、`text`、`card_id`
2. 选择对应时机的模板注册表
3. 按优先级顺序遍历模板
4. 首个命中的模板调用 `builder`
5. 返回生成的能力对象
6. 若全部未命中，则走现有 `semantic_map` / `UNSUPPORTED` 回退逻辑

这样主函数只保留分发职责，不再承载具体模板实现细节。

### 3. 通用模板与按卡特例分层

模板分两层维护：

#### 通用模板

优先承载可复用于多张卡的文本模式，例如：

- 固定抽牌
- 单体退场
- 目标选择后移动
- 生命区回手
- AP 激活
- 预览牌库后加手 / 登场 / 重排
- 临时 BP 修正
- 临时关键词授予
- 满足条件后替换数值阈值

这类模板必须优先使用已有原子 requirement / target / step 组合实现，不允许重新引入按卡解释逻辑。

其中，“预览牌库后按名称/特征加手并重排”应明确作为一个模板族维护，`UA31BT_MMM_1_007` 是该模板族的代表样例，而不是孤立个案。该模板族的 builder 应统一复用现有 `_preview_add_to_hand_then_reorder_steps(...)`，并通过参数注入差异，而不是按整句卡文继续复制 builder。

该模板族至少应支持以下参数：

- `preview_count`
- `candidate_filters`
- `candidate_requirements`
- `discard_after_add`
- `reorder_to_position`

文档约定下列文本变体优先归入同一模板族，再通过参数和附加过滤器表达差异：

- `〈某名称〉或［特徴：某特征］`
- `［特徴：某特征］`
- `〈某名称〉以外の［特徴：某特征］`

#### 特例模板

仅用于以下场景：

- 当前文本模式尚未抽象成稳定通用模板
- 某些卡在同一文本语义下存在额外限制条件
- 需要先维持现有支持结果，后续再继续泛化

即使是特例模板，也必须进入统一注册表，不允许散落回主调度函数中继续堆叠 `if card_id == ...`。

同时增加一条硬约束：如果某张新卡与既有模板相比，变化仅限于筛选值、名称、特征、预览张数或是否成功加入手牌后追加弃牌，则不得因为“先兼容再说”而登记为新的特例模板。只有当文本引入新的步骤组合、额外条件结算、或现有 builder 无法表达的控制流时，才允许落为特例模板。

### 4. 复用现有步骤构造器

当前脚本已经存在一批有价值的原子构造器，应继续保留并扩展，例如：

- 手动单体目标选择
- 上下文目标选择
- 从手牌过滤登场
- 从场外过滤登场
- 预览牌库后加手并重排
- 预览牌库后登场并重排
- 保留顶部其余送场外

后续模板 builder 不应在主流程中直接拼长段 steps，而应尽量通过这些构造器组合产出能力。这样识别层关注“匹配哪一种文本模式”，构造层关注“该模式如何被 IR 表达”。

### 5. 先不外置到 JSON

本轮不建议直接把识别规则外置成 JSON 或卡面配置文件，原因如下：

- 当前 builder 仍包含较多 Python 级别的组合逻辑
- 正则提取结果与条件化 steps 的拼装还需要代码表达能力
- 过早外置配置会把复杂度从代码结构问题转移为配置解释器问题

因此本轮的边界是：

- 先完成“代码内模板注册表化”
- 暂不推进“完全数据驱动化”

等模板结构稳定、builder 进一步标准化后，再评估是否有必要把部分精确匹配模板继续外置。

## 实施步骤

### 第一阶段：抽象模板基础设施

- 新增统一模板基类或轻量规则结构
- 封装精确文本匹配与正则匹配的公共入口
- 封装模板注册与按优先级遍历机制
- 保留 `_supported_ability`、`_unsupported_ability` 作为最终能力生成出口

### 第二阶段：迁移高复用模板族

优先迁移最重复、最稳定的模板族：

- 抽牌类
- 退场类
- 目标选择并移动类
- 临时 BP / 临时关键词类
- 预览牌库类
- 生命区回手后二次结算类

这一阶段的目标不是一次性迁完所有分支，而是先建立稳定迁移范式，让后续规则继续按同样方式搬迁。

在这一阶段内，必须额外完成“参数化收口”：

- 先识别每个模板族的固定部分与可变参数
- 优先收口“预览牌库类”中已经出现重复的文本模式
- 对现有分支建立归并表，至少覆盖：
  - 纯名称匹配
  - 纯特征匹配
  - 名称/特征 OR 匹配
  - 名称排除 + 特征匹配
  - 加手成功后追加弃牌
- 迁移完成后，同族新增卡文本应只需要补 matcher 的参数抽取，不应新增 builder 逻辑

### 第三阶段：收口现有卡号特例

- 把现有散落在 `_compile_trigger` / `_compile_event_effect` 中的卡号特例搬入特例模板注册表
- 保证特例仍可运行，但主调度函数不再感知具体卡号
- 对可继续泛化的特例，补充注释标记后续可合并方向

### 第四阶段：补充调试与统计辅助

建议为模板系统增加最小可观测性：

- 模板名称
- 命中次数统计
- 未命中回退计数
- 可选的调试输出开关

这样后续可以快速定位：

- 哪类模板命中异常下降
- 哪些文本被错误的泛化模板提前吞掉
- 哪些未支持项仍值得优先抽象

## 接口与兼容性要求

本次重构不改变以下对外契约：

- `data/cards/cards_effects.json` 的结构
- `data/cards/cards_semantic.json` 的结构
- `abilities[*].timing / requirements / target_specs / steps / limits / ui / status` 字段形状
- `core/effect_resolver.gd` 的运行时消费方式
- `DeckImporter`、`GameManager` 对编译结果文件的读取方式

允许变化的仅限于：

- `tools/compile_cards_effects.py` 内部组织结构
- 模板函数的拆分方式
- 识别流程的实现方式
- 调试统计输出的内部辅助信息

## 测试方案

### 编译回归

执行：

```powershell
python tools/compile_cards_effects.py
```

检查：

- 能正常输出 `cards_effects.json`
- 能正常输出 `cards_semantic.json`
- 已支持 / 未支持统计结果不出现非预期回退

### 产物等价性检查

至少抽样复核以下模板族的输出是否保持一致：

- 固定抽牌
- 单体退场
- 生命区回手
- AP 激活
- 预览牌库后加手
- 预览牌库后登场
- 临时 BP / 临时关键词授予

重点关注：

- `timing`
- `requirements`
- `target_specs`
- `steps`
- `status`

### 同类兼容性验收

针对 `UA31BT_MMM_1_007` 所代表的“预览牌库后按名称/特征加手并重排”模板族，至少增加以下验收标准：

- 准备一组仅替换特征名的假想文本或样例文本，确认其会命中同一模板族，而不是落为新的逐句模板
- 对“名称或特征”与“名称排除 + 特征”两种变体，确认最终 `steps` 主链保持一致，只允许 `filters` / `requirements` 差异
- 若启用模板统计，要求这些文本命中同一模板名或同一模板族标识
- 对产物比对，重点确认以下主链不因参数变化而分叉为新的专用实现：
  - `PREVIEW_TOP_DECK`
  - `SELECT_TARGETS`
  - `MOVE_SELECTED_CARDS`
  - `REORDER_CONTEXT_CARDS`

### 冒烟验证

执行现有验证脚本：

```powershell

res://docs/milestone_smoke_test.gd
```

确认：

- 既有已支持模板没有因为识别重构产生运行时回归
- 规则高风险区未受影响
- 未出现新增脏状态、延迟效果残留或目标选择异常

### 模板命中自检

若加入模板统计辅助，应至少确认：

- 每类核心模板都存在命中记录
- 未出现所有文本都落回 `UNSUPPORTED` 的回退异常
- 泛化模板不会吞掉更具体模板的命中机会

## 风险与注意事项

- 泛化模板优先级如果设置不当，可能会提前命中特例文本，导致行为细微偏差
- 正则模板迁移时要谨慎处理数值提取与条件替换，避免把“固定值模板”和“动态阈值模板”混成一类
- 特例模板短期内仍会存在，但必须被限制在注册表层，不能重新回流到主编译函数
- 若某张卡当前仍无法由现有 IR 稳定表达，保持 `UNSUPPORTED` 比引入新的按卡硬编码更安全
- 注册表模板化本身不是完成标准；若没有进一步收口为参数化模板族，后续仍会重复制造“换一个 trait/name 就新增一条模板”的维护成本

## 默认决策

本方案默认采用以下决策：

- 先做“注册表模板化”，不先做 JSON 外置
- 先重构识别层，不同步扩展新的 DSL/IR 能力
- 保持现有编译产物结构完全兼容
- 保留少量必要特例，但必须进入统一模板注册机制
- 优先迁移高复用模板族，再收口余下特例
- 对 `UA31BT_MMM_1_007` 这类同族文本，默认以“同一模板族参数化兼容”为完成标准，而不是仅迁移为多个注册表条目

## 预期收益

完成后，`compile_cards_effects.py` 的新增成本会从“修改一个持续膨胀的大函数”转为“新增一个模板规则并复用已有构造器”，带来以下收益：

- 识别入口更短、更稳定
- 模板复用关系更清晰
- 后续支持新卡效时更容易定位落点
- 更方便做命中统计、漏识别排查和局部回归验证
- 为未来进一步拆分模块或逐步数据驱动化打下基础
