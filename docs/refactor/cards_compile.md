# `compile_cards_effects.py` 识别模式重构方案

建议落盘路径：`docs/refactor/compile_cards_effects_recognizer_refactor.md`

## 概要

当前 `tools/compile_cards_effects.py` 的主要问题不是单纯文件过长，而是“识别规则、能力构造、少量卡号特例、回退逻辑”混在同一层顺序判断里。随着效果文本和支持卡池继续增长，继续沿用 `if text == ...` / `re.fullmatch(...)` 的线性堆叠方式，会持续放大以下成本：

- 新增模板时难以判断应插入的位置，容易误伤已有优先级
- 通用模板与按卡特例混杂，复用关系不清晰
- `_compile_trigger`、`_compile_event_effect`、`_compile_passive_effect` 会持续膨胀
- 后续想统计模板命中、排查漏识别、做局部回归都不方便

本次重构的目标是将识别模式改为“模板注册表 + 通用能力构造器”的结构，在不改变现有 `cards_effects.json` / `cards_semantic.json` 输出契约的前提下，降低维护成本并为后续扩展留出稳定入口。

## 重构目标

- 将“文本识别”与“能力组装”从主编译函数中拆开
- 将通用模板与按卡特例统一纳入注册表管理
- 保持现有 DSL/IR 输出字段不变，不修改运行时消费契约
- 让新增效果支持时，优先表现为“新增模板”而不是“继续扩展大函数”
- 保留未支持能力的回退链路与 `semantic_map` 分析能力

## 设计方案

### 1. 引入统一模板规则模型

为识别层引入统一的模板描述结构。每条模板至少包含以下信息：

- `name`
  - 模板名称，用于调试和统计命中情况
- `event_filter`
  - 适用时机，例如 `ON_ENTER`、`ON_PLAY`、`MAIN_ACTIVATE`、`ON_LIFE_TRIGGER`
- `matcher`
  - 文本匹配器，支持精确文本匹配和正则匹配
- `card_filter`
  - 可选的卡号白名单或谓词，用于保留少量必要的按卡特例
- `builder`
  - 命中后负责组装 `requirements`、`target_specs`、`steps` 并返回能力对象
- `priority`
  - 用于控制模板匹配顺序，具体模板优先于泛化模板
- `kind_override`
  - 可选，用于覆盖 `TRIGGERED` / `ACTIVATED`
- `unsupported_reason`
  - 可选，用于部分支持或显式未支持模板

模板规则只负责两件事：

- 判断当前卡面文本是否命中
- 将命中的文本映射为统一 DSL/IR 能力对象

模板规则不负责直接写文件，不负责跨模板决策。

### 2. 将主编译入口改为调度器

把以下函数改造成调度器，而不是长链判断：

- `_compile_trigger`
- `_compile_event_effect`
- `_compile_passive_effect`

调度流程统一为：

1. 读取 `event_name`、`text`、`card_id`
2. 选择对应时机的模板注册表
3. 按优先级顺序遍历模板
4. 首个命中的模板调用 `builder`
5. 返回生成的能力对象
6. 若全部未命中，则走现有 `semantic_map` / `UNSUPPORTED` 回退逻辑

这样主函数只保留分发职责，不再承载具体模板实现细节。

### 3. 通用模板与按卡特例分层

模板分两层维护：

#### 通用模板

优先承载可复用于多张卡的文本模式，例如：

- 固定抽牌
- 单体退场
- 目标选择后移动
- 生命区回手
- AP 激活
- 预览牌库后加手 / 登场 / 重排
- 临时 BP 修正
- 临时关键词授予
- 满足条件后替换数值阈值

这类模板必须优先使用已有原子 requirement / target / step 组合实现，不允许重新引入按卡解释逻辑。

#### 特例模板

仅用于以下场景：

- 当前文本模式尚未抽象成稳定通用模板
- 某些卡在同一文本语义下存在额外限制条件
- 需要先维持现有支持结果，后续再继续泛化

即使是特例模板，也必须进入统一注册表，不允许散落回主调度函数中继续堆叠 `if card_id == ...`。

### 4. 复用现有步骤构造器

当前脚本已经存在一批有价值的原子构造器，应继续保留并扩展，例如：

- 手动单体目标选择
- 上下文目标选择
- 从手牌过滤登场
- 从场外过滤登场
- 预览牌库后加手并重排
- 预览牌库后登场并重排
- 保留顶部其余送场外

后续模板 builder 不应在主流程中直接拼长段 steps，而应尽量通过这些构造器组合产出能力。这样识别层关注“匹配哪一种文本模式”，构造层关注“该模式如何被 IR 表达”。

### 5. 先不外置到 JSON

本轮不建议直接把识别规则外置成 JSON 或卡面配置文件，原因如下：

- 当前 builder 仍包含较多 Python 级别的组合逻辑
- 正则提取结果与条件化 steps 的拼装还需要代码表达能力
- 过早外置配置会把复杂度从代码结构问题转移为配置解释器问题

因此本轮的边界是：

- 先完成“代码内模板注册表化”
- 暂不推进“完全数据驱动化”

等模板结构稳定、builder 进一步标准化后，再评估是否有必要把部分精确匹配模板继续外置。

## 实施步骤

### 第一阶段：抽象模板基础设施

- 新增统一模板基类或轻量规则结构
- 封装精确文本匹配与正则匹配的公共入口
- 封装模板注册与按优先级遍历机制
- 保留 `_supported_ability`、`_unsupported_ability` 作为最终能力生成出口

### 第二阶段：迁移高复用模板族

优先迁移最重复、最稳定的模板族：

- 抽牌类
- 退场类
- 目标选择并移动类
- 临时 BP / 临时关键词类
- 预览牌库类
- 生命区回手后二次结算类

这一阶段的目标不是一次性迁完所有分支，而是先建立稳定迁移范式，让后续规则继续按同样方式搬迁。

### 第三阶段：收口现有卡号特例

- 把现有散落在 `_compile_trigger` / `_compile_event_effect` 中的卡号特例搬入特例模板注册表
- 保证特例仍可运行，但主调度函数不再感知具体卡号
- 对可继续泛化的特例，补充注释标记后续可合并方向

### 第四阶段：补充调试与统计辅助

建议为模板系统增加最小可观测性：

- 模板名称
- 命中次数统计
- 未命中回退计数
- 可选的调试输出开关

这样后续可以快速定位：

- 哪类模板命中异常下降
- 哪些文本被错误的泛化模板提前吞掉
- 哪些未支持项仍值得优先抽象

## 接口与兼容性要求

本次重构不改变以下对外契约：

- `data/cards/cards_effects.json` 的结构
- `data/cards/cards_semantic.json` 的结构
- `abilities[*].timing / requirements / target_specs / steps / limits / ui / status` 字段形状
- `core/effect_resolver.gd` 的运行时消费方式
- `DeckImporter`、`GameManager` 对编译结果文件的读取方式

允许变化的仅限于：

- `tools/compile_cards_effects.py` 内部组织结构
- 模板函数的拆分方式
- 识别流程的实现方式
- 调试统计输出的内部辅助信息

## 测试方案

### 编译回归

执行：

```powershell
python tools/compile_cards_effects.py
```

检查：

- 能正常输出 `cards_effects.json`
- 能正常输出 `cards_semantic.json`
- 已支持 / 未支持统计结果不出现非预期回退

### 产物等价性检查

至少抽样复核以下模板族的输出是否保持一致：

- 固定抽牌
- 单体退场
- 生命区回手
- AP 激活
- 预览牌库后加手
- 预览牌库后登场
- 临时 BP / 临时关键词授予

重点关注：

- `timing`
- `requirements`
- `target_specs`
- `steps`
- `status`

### 冒烟验证

执行现有验证脚本：

```powershell
res://docs/cards_raw_minimal_duel_smoke_test.gd
res://docs/milestone_smoke_test.gd
```

确认：

- 既有已支持模板没有因为识别重构产生运行时回归
- 规则高风险区未受影响
- 未出现新增脏状态、延迟效果残留或目标选择异常

### 模板命中自检

若加入模板统计辅助，应至少确认：

- 每类核心模板都存在命中记录
- 未出现所有文本都落回 `UNSUPPORTED` 的回退异常
- 泛化模板不会吞掉更具体模板的命中机会

## 风险与注意事项

- 泛化模板优先级如果设置不当，可能会提前命中特例文本，导致行为细微偏差
- 正则模板迁移时要谨慎处理数值提取与条件替换，避免把“固定值模板”和“动态阈值模板”混成一类
- 特例模板短期内仍会存在，但必须被限制在注册表层，不能重新回流到主编译函数
- 若某张卡当前仍无法由现有 IR 稳定表达，保持 `UNSUPPORTED` 比引入新的按卡硬编码更安全

## 默认决策

本方案默认采用以下决策：

- 先做“注册表模板化”，不先做 JSON 外置
- 先重构识别层，不同步扩展新的 DSL/IR 能力
- 保持现有编译产物结构完全兼容
- 保留少量必要特例，但必须进入统一模板注册机制
- 优先迁移高复用模板族，再收口余下特例

## 预期收益

完成后，`compile_cards_effects.py` 的新增成本会从“修改一个持续膨胀的大函数”转为“新增一个模板规则并复用已有构造器”，带来以下收益：

- 识别入口更短、更稳定
- 模板复用关系更清晰
- 后续支持新卡效时更容易定位落点
- 更方便做命中统计、漏识别排查和局部回归验证
- 为未来进一步拆分模块或逐步数据驱动化打下基础
