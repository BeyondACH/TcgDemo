## Architecture

### Core Modules (`core/`)
- **`game_manager.gd`**: Central coordinator exposing game actions, managing state snapshots, and emitting signals to UI
- **`turn_manager.gd`**: Phase progression (DRAW → MOVE → MAIN → ATTACK → END), AP growth, bonus draw, hand limit enforcement
- **`rules_engine.gd`**: Validation layer for card play, movement, attacks, energy/AP costs, zone capacity
- **`effect_resolver.gd`**: Effect queue consumption, trigger resolution, target selection, cost payment, DSL/IR execution
- **`battle_resolver.gd`**: Attack declaration, blocking, BP comparison, damage calculation, battle triggers
- **`zone_manager.gd`**: Card movement between zones, zone capacity checks, shuffling, RAID stacking
- **`victory_checker.gd`**: Win condition detection (life empty, deck-out draw failure)

### Data Models (`data/`)
- **`game_state.gd`**: Runtime state including players, cards, effect queue, pending decisions, battle context
- **`player_state.gd`**: Per-player zones (deck, hand, life, front_line, energy_line, ap_area, outside, removed)
- **`card_def.gd`**: Static card definition with cost, BP, keywords, effects, trigger_effects
- **`card_instance.gd`**: Runtime card instance with uid, zone, state, flags, stacked_under

### UI Layer (`ui/`)
- **`battle_scene.gd`**: Main scene consuming `get_snapshot()`, routing user interactions to GameManager
- **`board_view.gd`**: Battlefield display with front line, energy line, life area, deck/outside zones
- **`hand_view.gd`**: Hand display with card thumbnails and drag-to-play
- **`card_view.gd`**: Individual card rendering with state/zone indicators

## Critical Constraints

### Zone Capacities (from `docs/rules/rule.md`)
- Front Line: max 4 characters
- Energy Line: max 4 cards (characters + fields combined)
- AP Area: max 3 slots
- Starting Life: 7 cards
- Starting Hand: 7 cards
- Main Deck: 50 cards
- Hand Limit (end phase): 8 cards

### Card State Rules
- Characters/Fields enter in RESTED state
- Only ACTIVE characters can attack or block
- AP cards do NOT ready during end phase
- Attacker does NOT leave play when BP is lower than blocker

## Card Effect DSL/IR Principles

From `AGENTS.md`:

1. **Code by atomic capability, not by card**: Never write card-specific logic; create reusable atomic requirements and steps
2. **Runtime consumes unified IR only**: No raw card text execution at runtime
3. **Strictly separate requirements from steps**:
   - Requirements: availability, legality, trigger conditions, filtering - never modify game state
   - Steps: atomic state changes only - no conditional branching or card-specific logic
4. **Explicit target selection**: Target selection enters pending decision flow; no auto-selecting first N candidates
5. **Mark unsupported cards**: Cards not expressible in current IR should be marked "暂不支持" rather than hardcoded

### Supported Trigger Types
`ON_ENTER`, `ON_LEAVE`, `ON_ATTACK`, `ON_BLOCK`, `ON_LIFE_TRIGGER`, `MAIN_ACTIVATE`, `ON_BATTLE_WIN`, `ON_BATTLE_LOSE`, `ON_BATTLE_END`, `ON_PLAY` (events)

## Key Keywords (implemented)
`STEP`, `SNIPER`, `DAMAGE_2`, `IMPACT`, `IMPACT_PLUS_1`, `NEGATE_IMPACT`, `DOUBLE_ATTACK`, `DOUBLE_BLOCK`, `RAID`
